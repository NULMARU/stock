# 스톡앱 내부 시뮬레이션 앱 개발계획

작성일: 2026-09-12 · 상태: 계획 수립 완료, 구현 전

갱신일: 2026-09-13. 관심 종목 재무제표·쉬운 해석 기능을 Stock 본체의 별도 개발 흐름으로 추가했다. 재무 기능의 범위·추가 일정은 아래 13절과 [재무제표 기능 계획](financial-statements-feature-plan.md)을 따른다.

**결정: 스톡앱 안에 독립된 작업 공간인 ‘시뮬레이션 랩’을 만들고, 계산 엔진·산업 모델·화면을 분리한다. 첫 제품 릴리스 전에 단위·자원 제약·시간 처리의 정합성을 확보한다.** 사용자는 스톡앱에서 들어오되 내부 앱에서는 시나리오 작성, 비교, 실행 기록, 가정과 근거 확인에 집중한다.

이 문서는 [초기 통합 검토](infrawheel-integration-review.md)의 후속 결정이다. 단일 산업 페이지 중심이던 안을 독립 레이아웃과 실행 이력을 갖춘 내부 앱으로 확대하고, 마지막 단계였던 모델 정합성 개선을 첫 릴리스의 선행 조건으로 옮긴다. 의사결정이 필요한 부분은 아래 기본안으로 정했으며 계획을 완료하기 위한 사용자 응답은 필요하지 않다.

관련 산출물: [모델 정밀도·검증 설계](simulation-model-validation.md), [개발 작업 목록](simulation-lab-backlog.md), [원본 엔진 실험 결과](evidence/infrawheel-engine-probe.json).

추가 산출물: [관심 종목 재무제표·12개 핵심 질문·AI 해석 계획](financial-statements-feature-plan.md).

## 1. 제품 범위와 기본 결정

| 항목 | 개발 기본안 |
|---|---|
| 내부 앱 이름 | 시뮬레이션 랩, 최초 탑재 모델은 InfraWheel |
| 진입 위치 | 스톡앱 메뉴 ‘시뮬레이션’, 종목 상세의 ‘산업에서 살펴보기’ |
| 주소 | 기존 Pages 경로 아래 `#/lab/*` |
| 독립성 | 별도 레이아웃·탐색·상태·저장소·오류 경계, 동일한 로그인 없는 정적 앱 배포 |
| 계산 방식 | 브라우저 Web Worker에서 순수 TypeScript 엔진 실행 |
| 첫 모델 | 단위·자원·분기 시간 처리를 수정한 InfraWheel 구조 모델 |
| 원본 모델 | `legacy-09c710e`로 고정하여 회귀 검증·이전 결과 설명에 보존 |
| 최초 해상도 | 분기. 월별은 별도 모델 검증 후 지원 |

| 사용자 수준 | 기본 14입력과 고급 개별 입력, 동일한 내부 파라미터 집합 사용 |
| 첫 배포 목표 | 가정의 변화와 산업 경로를 비교하는 구조적 시뮬레이션 |

초기 시뮬레이션 범위에는 계정·시뮬레이션 서버 실행·팀 공동 편집·원격 플러그인·자동 주문 기능을 범위에 넣지 않는다. 공급 병목이 특정 종목의 수익을 높이거나 낮추는지는 가격 결정력·비용·고객 구조에 따라 달라지므로 종목 연결은 관계와 근거를 보여주는 기능으로 시작한다.

## 2. 내부 앱의 사용자 흐름

1. **내 실험실:** 프리셋, 최근 시나리오, 최근 실행, JSON 가져오기. 최초 실행은 사용자가 시작할 수 있는 기준 시나리오를 제공한다.
2. **시나리오 편집:** 이름, 기준 시점, 계산 기간, 모델, 입력 가정, 사건 타임라인을 편집한다. 출처 없는 입력은 ‘사용자 가정’으로 식별한다.
3. **실행·비교:** 기준과 대안 1개를 기본 비교하고 최대 3개 대안을 허용한다. 수정 중에는 ‘미실행 변경’ 상태를 표시한다. 실행은 입력 사본을 고정한다.
4. **결과 탐색:** 6개 노드 휠, 시간 차트, 병목의 시작·지속·해소, 공급 충족률, 매출·CAPEX, 계산 근거를 본다. 마지막 분기뿐 아니라 전체 경로와 누적 차이를 비교한다.
5. **민감도·불확실성:** 검증 단계에 맞춰 입력 범위별 차이, 이후 확률 분포 기반 범위를 탐색한다. 기존 `confidence` 변수는 ‘재투자 반영 계수’로 설명하며 예측 신뢰도와 구분한다.
6. **기록·연결:** 실행 결과와 가정을 저장하고 관련 종목·뉴스를 확인하거나 스톡앱으로 복귀한다.

데스크톱은 왼쪽 시나리오·입력, 가운데 휠·타임라인, 오른쪽 결과 근거·관련 종목을 배치한다. 좁은 화면에서는 ‘가정 / 결과 / 근거’ 탭으로 바꾸고 비교 표는 항목별로 전환한다. 차트에는 같은 데이터를 읽을 수 있는 표를 제공한다. 기본 한국어, 단위·기간·실행 상태를 항상 확인할 수 있게 한다.

내부 앱 헤더는 ‘스톡앱으로’, 시나리오명, 저장 상태, 실행/취소, 비교 메뉴로 구성한다. 기존 스톡앱 티커바와 종목용 메뉴는 내부 앱에 중복 표시하지 않는다. 스톡앱 복귀 시 이전 종목·필터·스크롤을 복원한다. 미완료 초안은 자동 저장하며, 저장 실패 상태에서는 파일로 내보낼 수 있게 한다.

## 3. 애플리케이션 경계

별도 iframe이나 원격 microfrontend 대신 **하나의 배포 안에 두 개의 레이아웃**을 둔다. URL과 상태를 통제하기 쉽고, 기존 앱과 시뮬레이션 간 이동 및 PWA를 하나로 검증할 수 있다. 나중에 별도 서비스로 분리할 때 계산 패키지와 내부 앱 모듈을 그대로 옮길 수 있게 의존 방향을 제한한다.

```text
App / HashRouter
  StockLayout                 # 종목·뉴스·용어, 기존 헤더·티커바
  SimulationLabLayout         # /lab/*, 별도 헤더·탐색·오류 경계
    Scenario / Comparison / Run / Evidence 화면
      ExecutionClient → Worker → simulation-core → infrawheel-model
      ScenarioRepository / RunRepository → IndexedDB
      StockContextAdapter → 읽기 전용 종목·뉴스·용어 데이터
```

| 라우트 | 역할 |
|---|---|
| `#/lab` | 내 시나리오와 실행 목록 |
| `#/lab/scenarios/:id` | 기기 내 시나리오 편집 |
| `#/lab/runs/:id` | 입력이 고정된 실행 결과 |
| `#/lab/compare?runs=…` | 호환되는 실행 결과 비교 |
| `#/lab/import?state=…` | 버전이 포함된 공유 시나리오 검증·가져오기 |

`id`만 있는 기기 내 주소는 다른 기기에서 열리지 않는다. ‘주소 복사’와 ‘시나리오 공유’를 UI에서 구분한다. 공유는 입력·모델 식별자를 담은 URL 또는 JSON 파일을 사용한다. 완성 URL 길이가 8 KiB를 넘으면 파일 공유로 전환한다. 메모·관심 종목·개인 기록은 공유 기본값에서 제외한다. 실행 결과 파일에는 입력과 결과, 참조 데이터 버전을 포함하며 이력 ID만 내보내지 않는다.

원본 store의 `location.hash` 읽기 및 `history.replaceState` 구독은 제거하고 React Router 경유 어댑터로 교체한다. UI 이동은 push, 연속 입력에 따른 상태 동기화는 replace로 처리한다. 잘못된 데이터는 사유를 보여주며 원본 파일을 보존하고, 알 수 없는 모델 버전을 현재 버전으로 조용히 바꾸지 않는다.

## 4. 코드와 패키지 구조

```text
package.json                          # 현재 루트 앱 유지 + npm workspaces
packages/
  simulation-core/src/                # 모델 계약, 단위·시간, 실행·검증·진단
  infrawheel-model/src/
    legacy/                           # 원본 동작 고정, 출처 보존
    v2/                               # 정합성 수정 모델
    metadata/                         # 변수·단위·가정·출처·호환성
src/
  layouts/StockLayout.tsx
  apps/simulation-lab/
    routes/ components/ styles/
    state/ persistence/ sharing/
    execution/                        # Worker 및 메시지 어댑터
    stock-context/                    # 종목 데이터와의 한 방향 연결
public/simulation-data/
  manifest.json
  <dataset-version>/                  # 변경 불가 데이터 스냅샷
scripts/simulation/                   # 보정·검증용 실행기, 데이터 변환
```

루트 Stock 앱 전체를 다른 폴더로 이전하지 않는다. 두 계산 패키지에 `exports`·타입 선언·명시적 빌드 순서를 추가한다. `simulation-core`는 모델 인터페이스만 알고 구체적인 InfraWheel 모델을 import하지 않는다. `infrawheel-model`이 인터페이스를 구현하고 앱의 모델 레지스트리가 조합한다. 코어에는 DOM, 네트워크, localStorage, React, 시계나 전역 난수 사용을 금지한다.

Stock은 기존 React 19·Vite 7·Tailwind 3를 유지한다. 내부 앱 차트는 기존 Recharts 2 API에 맞춘 작은 어댑터로 이식한다. Recharts 3 마이그레이션은 기존 주가 차트·툴팁·범례까지 검증하는 후속 작업이다. Zustand는 내부 앱의 편집·선택 상태에만 사용하며 계산 결과 생성 로직은 저장소 밖으로 옮긴다. 신규 테스트는 패키지/Worker/라우터/브라우저에 맞는 실행기로 구성한다.

스타일은 CSS Modules와 `--sim-*` 토큰으로 제한하고, 원본 전역 reset·문서 `lang` 변경·100vh 고정을 가져오지 않는다. 전역 Tailwind가 내부 앱에 미치는 영향도 함께 확인한다. 내부 앱 오류 경계는 실패한 입력과 마지막 정상 실행을 유지하고 스톡앱 복귀를 제공한다.

## 5. 실행 계약과 재현성

**Scenario는 편집 가능하고, Run은 실행 당시의 입력과 결과가 고정된 기록이다.** 화면에서 입력을 바꿔도 과거 실행의 의미가 바뀌지 않는다.

| 계약 | 핵심 필드 |
|---|---|
| ScenarioDocument | schemaVersion, id, revision, title, modelId, modelVersion, baselineId, timeline, inputs, events |
| ResolvedRunInput | modelVersion, engineVersion, calibrationVersion, datasetVersion, adapterVersion, 단위 변환 후 inputs, initialState, events, timeStep, seed, samplingSpec |
| RunArtifact | runId, scenarioRevision, inputHash, resolvedInput, series, diagnostics, evidenceRefs, resultHash, executionMetadata |
| MetricDefinition | id, label, unit, stock/flow/index 구분, 집계 방식, 비교 가능 범위 |
| DatasetManifest | version, contentHash, source, observationDate, publishedAt, retrievedAt, geography, unit, coverage, redistributionStatus |

입력은 스키마·유한수·단위·범위·기간·예산 제약을 통과한 후 실행한다. UI 슬라이더 범위와 엔진의 물리적 경계를 구분한다. 예를 들어 UI의 일반 전력 범위보다 낮은 충격을 모델링하더라도 음수나 이중 자원 배분은 허용하지 않는다. 알 수 없는 필드/단위와 자동 보정한 필드는 진단에 남긴다.

정렬 규칙이 있는 canonical JSON에서 표현용 이름·생성 시각을 제외하고 SHA-256 입력 해시를 만든다. 모든 실행 의미에 영향을 주는 버전·초기 상태·분포·상관 설정은 포함한다. 난수를 쓰면 seed와 PRNG 알고리즘 버전을 저장하고 샘플 번호별 난수열을 고정하여 Worker 수와 완료 순서에 결과가 의존하지 않게 한다. 같은 빌드/런타임에서의 반복 재현성과 런타임 간 수치 허용오차를 별도로 검증한다.

기본 실행 순서는 `입력 검증 → 버전 고정 → 기준 상태 구성 → 분기별 계산 → 불변조건 검증 → 결과 요약 → 저장`이다. 무효 입력은 부분 실행 결과로 정상 처리하지 않는다. 모델 간 비교는 단위·지역·기준시점·기간이 같을 때만 허용한다. 다른 모델 버전은 ‘모델 변경 비교’로 명시한다.

## 6. 비동기 계산과 저장

Worker 계약은 `run / cancel / progress / result / error` 메시지와 `requestId`, `inputHash`를 사용한다. 늦게 도착한 이전 실행 결과가 새 시나리오를 덮어쓰지 못하게 한다. 짧은 단일 실행은 변경 후 debounce 미리보기를 제공할 수 있으나, 저장할 정식 실행 및 대량 샘플링은 ‘실행’ 동작으로 고정한다.

취소 메시지는 동기 계산 중인 Worker에 즉시 처리되지 않을 수 있으므로 샘플 배치 사이에 제어를 반환한다. 단일 긴 작업은 Worker terminate 후 재생성하는 취소 경로를 둔다. 기본 Worker 1개, 대량 계산 병렬화는 성능 측정 후 제한된 수로 확장한다. 모델 코드를 문자열로 내려받거나 사용자가 업로드한 코드를 실행하지 않는다.

IndexedDB는 시나리오, 실행, 데이터 스냅샷, 마이그레이션 기록을 나눈다. 초안 자동 저장은 한 트랜잭션으로 처리하고 저장 용량 초과 시 메모리 작업과 파일 내보내기를 유지한다. 기준 시나리오·사용자가 고정한 실행은 자동 정리하지 않는다. 재계산 가능한 임시 캐시부터 LRU로 제거한다. 같은 문서의 다중 탭 저장은 revision 비교로 충돌을 감지하고 사본으로 보존한다.

V1은 시나리오 100개와 고정 실행 100개를 검증 규모로 삼는다. 샘플링 결과는 기본적으로 분위수·요약을 저장하고 전체 경로 보존은 별도 선택으로 둔다. 이 수치는 브라우저 저장 보장을 의미하지 않으며 실제 데이터 크기와 저장 실패 경로를 검증한다.

## 7. 정밀도 개선 순서

정밀도는 ① 계산과 단위가 맞는지, ② 공급·수요의 구조가 타당한지, ③ 관측 데이터를 얼마나 설명하는지, ④ 알려지지 않은 값의 불확실성을 얼마나 정직하게 표현하는지로 나눈다. 소수 자릿수 증가나 시나리오 수 증가를 정확도 향상으로 취급하지 않는다.

| 단계 | 목표 | 릴리스에서 허용하는 설명 |
|---|---|---|
| Legacy | 원본 154개 테스트의 의미와 기존 결과 보존 | 원본 호환 결과 |
| Structural v2 | 단위·시간·공급 제약·재투자 처리 검증 | 입력 가정에 따른 구조적 시뮬레이션 |
| Calibrated v2.x | 공개·허용 데이터로 계수 보정, 시간 분리 평가 | 검증된 지표·지역·기간에 한정한 오차 공개 |
| Uncertainty v2.x | 민감도, 분포·상관·샘플 오차 분석 | 가정한 분포에 따른 조건부 범위 |
| Extended v3+ | 지역 네트워크·다른 산업·월별 계산 | 확장별 별도 모델 검증 후 제공 |

첫 릴리스는 Structural v2가 목표다. 관측 데이터가 부족하면 해당 계수는 가정 상태를 유지하고, 결과에 ‘보정 완료’나 예측 적중률을 붙이지 않는다. ‘확률 80%’도 입력 분포만 임의로 설정해서 확정하지 않는다. 정밀도별 완료 기준과 수식은 [검증 설계](simulation-model-validation.md)를 따른다.

## 8. 정밀도와 확장성을 위한 설계 결정

- **UI 노드와 계산 노드 분리:** 6개 노드는 설명용 보기다. 내부 모델이 전력망·메모리·파운드리·훈련/추론 등으로 세분화돼도 화면 계약은 어댑터가 유지한다.
- **기본/고급 입력 일관성:** 고급 모드에서 개별 값을 편집한 뒤 기본 화면으로 돌아와도 복합 지수로 역변환하여 원값을 덮어쓰지 않는다. 기본 화면에는 ‘개별 조정’ 상태를 표시한다.
- **사건 확장:** 컴파일 시 등록된 `EventDefinition`으로 입력 채널·단위·기간·결합 규칙을 선언한다. 현재의 고정된 RiskId 3개와 단방향 포화 결합을 범용 인터페이스 뒤로 옮긴다. 공급 회복·보조금·가격 상승처럼 방향이 다른 충격은 결합 순서와 중복 원인을 정의한다.
- **데이터 경계:** 종목 시세 갱신이 과거 시뮬레이션을 자동 변경하지 않는다. 기준 데이터 세트가 바뀌면 새 시나리오 revision과 새 실행을 만든다.
- **연산 확장:** 브라우저 Worker와 향후 서버 실행기가 같은 입력·출력 계약을 구현한다. 시뮬레이션 서버 실행은 장시간 배치·공동 사용·비공개 데이터 요구가 실제로 발생할 때 추진한다. 재무 최신 조회용 API·수집 Worker는 이와 별개로 FR0에서 도입한다.
- **지역 확장:** 국가 노드 추가 시 기존 글로벌 총량을 복제하지 않는다. 지역별 생산·소비·교역 및 중복 집계 규칙을 먼저 정의한다. 우주·방산은 같은 6노드에 억지로 편입하지 않고 별도 모델로 추가한다.

## 9. 배포·오프라인·성능 기준

Stock 메뉴에서는 내부 앱 코드와 모델 데이터를 다운로드하지 않고 진입 시 lazy-load한다. Vite의 상대 base와 Worker 에셋 경로를 실제 `/stock/` 배포 경로에서 확인한다. 기존 `public/sw.js`의 전역 캐시 삭제, 즉시 skipWaiting/claim 정책을 앱 식별 prefix·버전 기반으로 바꾸고 진행 중 실행·저장이 있을 때 업데이트를 적용하지 않는다.

사용자는 ‘오프라인 준비’를 실행해 내부 앱 chunk·Worker·모델·선택 데이터 스냅샷의 완전한 캐시를 확보한다. 준비가 성공한 버전만 오프라인 가능으로 표시한다. manifest와 해시로 버전이 섞인 데이터를 거부한다. `/simulation-data/`는 기존 최신 JSON 갱신 경로와 분리해 불변 버전으로 캐시한다. 새 버전 설치가 실패하면 이전의 완전한 버전을 유지한다.

아래는 **달성 여부를 측정할 초기 예산**이며 현재 보장값이 아니다. 구현 첫 단계에서 데스크톱 Chromium과 Android 중급 기기 또는 명시적으로 기록한 대체 환경을 고정한다.

| 지표 | 초기 목표 |
|---|---|
| Stock 초기 JS 증가 | gzip 10 KiB 이하, 라우팅·진입 링크 수준 |
| 내부 앱 초기 추가 JS | gzip 300 KiB 이하, 공유 라이브러리 제외 |
| 단일 44분기 실행 | 기준 환경 p95 200 ms 이하, Worker 왕복·요약 포함 |
| 입력 반응 | 메인 스레드 반응 100 ms 이내, 50 ms 초과 작업 원인 추적 |
| 1,000개 샘플 × 44분기 | p95 5초 이내를 초기 목표로 측정, 초과 시 샘플 단계별 실행 |
| 취소 | 동작 후 200 ms 이내 진행 종료 상태 반영 |
| 반복 진입 | 20회 진입·해제 후 Worker·구독 누적 없음 |
| 오프라인 | 준비 완료한 시나리오 생성·실행·저장·재열기 가능 |

원본 로컬 Node 실험은 기준+지정학 44분기 실행의 p95 약 0.34 ms였다. 이는 원본 계산량이 작다는 참고일 뿐, 정합성 수정 모델·브라우저 렌더·모바일·샘플링 성능을 보장하지 않는다.

## 10. 일정과 릴리스 기준

다음은 **1명의 숙련 개발자가 순차 수행하는 계획상 실작업일 추정**이다. 자동화 도구가 처리하는 시간이나 달력상의 완료 약속이 아니다. 외부 데이터 제공·도메인 검토 대기 기간은 포함하지 않는다. 작업 상세와 의존성은 [백로그](simulation-lab-backlog.md)에 있다.

| 단계 | 작업일 | 결과와 통과 조건 |
|---|---:|---|
| P0. 기반·계약 | 3–4 | 내부 앱 골격, 패키지 경계, 원본 회귀 기준, 실행 스키마 |
| P1. 모델 정합성 | 8–12 | 단위·자원 배분·시간·투자 원장·진단. 검증 설계의 필수 불변조건 통과 |
| P2. 실험실 기능 | 7–10 | Worker, 편집·실행·비교·저장·가져오기, 오류 복구 |
| P3. Stock 연결·출시 검증 | 4–6 | 종목 연결, 모바일·접근성·PWA·업데이트·회귀 검증 |

| P4. 데이터 보정 | 8–12 | 출처·시점 관리, 기준선 비교, 시간 분리 평가, 모델 카드 |

P1과 P2는 API 경계를 고정한 뒤 논리적으로 병행 가능하지만 위 수치는 병렬 인력 투입을 가정하지 않는다. 데이터 부족 시 P4를 ‘검증 불가 지표와 확보 계획’으로 명시하고 P5의 범위를 가정 기반 분석으로 제한한다. 실패한 관측 검증을 통과한 것으로 간주해 다음 등급으로 올리지 않는다.

완료 조건은 화면이 실행되는 것 이상이다. 저장한 입력의 재실행, 모델 버전 추적, 단위·자원·시간 검증, 기준과 대안 비교, 오류·취소·저장 실패 복구, Stock 회귀, 오프라인 및 업데이트 일관성까지 통과해야 한다. 신규 코드의 lint 오류는 0개이며 기존 9개 오류·2개 경고는 기준 목록으로 고정하거나 관련 파일 수정 시 함께 해결한다. CI 전체 실패를 정상 통과처럼 처리하지 않는다.

## 11. 첫 구현 변경 묶음

첫 PR은 `StockLayout` 분리, `/lab/*` 빈 작업 공간과 오류 경계, 두 계산 패키지, 원본 엔진과 출처·회귀 테스트, 버전이 있는 입력·결과 스키마까지로 제한한다. 기존 종목 화면 동작과 빌드가 유지되고 코어에서 브라우저 의존성을 import하지 않는 것을 확인한다. 이 상태는 개발 기반이며 일반 사용자용 시뮬레이터 출시에 해당하지 않는다.

다음 PR은 단위·시간 계약과 독립 계산 예제를 먼저 추가하고 Structural v2를 구현한다. 기존 snapshot을 새 계산에 맞춰 덮어써서 통과시키지 않고 legacy 결과와 v2 결과의 차이를 따로 설명한다. 이후 Worker와 작업 공간 기능을 연결한다.

원본 저장소의 미확인 저작권·출처 사항은 기존 `UPSTREAM_SOURCE.md`에 따라 출처를 보존하고 공개 배포 전에 정리한다. 계획 수립이나 로컬 정합성 검증을 중단시키는 조건으로 취급하지 않는다.

## 13. 관심 종목 재무제표 기능 추가 — 2026-09-13

Stock 본체에 `#/stock/:ticker/financials` 경로와 관심 종목 카드의 ‘재무 보기’를 추가한다. `재무 요약 / 재무제표 / 심화 해석`에서 3개 주요 재무제표, 기간별 추세, 원문 근거와 함께 아래 질문을 제공한다. 기존 26개 상세 페이지에 없는 검색 추가 종목도 발행회사 식별·지원 상태에 따라 진입할 수 있도록 설계한다.

| 분석 영역 | 핵심 질문 |
|---|---|
| 안정성 | 빚·이자를 감당할 수 있나? 단기 지급 여력이 있나? |
| 수익성 | 이익이 반복 가능한가? ROE 상승은 실제 효율 개선인가? |
| 성장성 | 매출 성장에 지속 근거가 있나? 투자가 성과로 돌아오나? |
| 현금흐름 | 이익이 현금으로 전환되나? 배당·자사주 매입 여력이 있나? |
| 가치평가 | 현재 가격에 어떤 기대가 반영됐나? 장부가 대비 평가 이유는 무엇인가? |
| 리스크 | 재고가 오래 묶이거나 손상될 위험은? 매출채권을 회수할 수 있나? |

계산·공시 사실·AI 추론·미확인 정보를 구분하고, 부도 확률·회계조작·수익률을 단일 비율에서 단정하지 않는다. 첫 재무 릴리스에서도 규칙 기반 쉬운 해석을 제공한다. 공시 주석·사업부·고객·차입 조건을 요구하는 AI 심화는 후속 단계에서 근거 검증을 거쳐 제공한다.

새 `packages/financial-analysis`가 재무 지표의 정의와 계산을 소유하고 `scripts/financials`가 공시 수집·정규화를 담당한다. 본체는 [최신 조회 API](financial-live-data-plan.md)에서 검증 스냅샷과 갱신 상태를 조회하고, 정적 자료는 오프라인·fallback에 사용한다. 원본 재무 데이터·공시 AI 해석은 브라우저 내 시뮬레이션 계산과 별도 처리하며 API 키는 서버/CI에서만 사용한다. 관심 목록은 기기에 저장하고, 화면에서 요청한 지원 발행회사에 한해 신규 수집·최신 공시 확인을 수행한다. 미지원 종목은 상태를 명시한다.

랩 연결은 별도 `corporate-finance-v1` 모델로 구현한다. 회사의 OCF·CAPEX·차입·운전자본 스냅샷을 고정해 금리·매출 회수·마진 변화 조건을 살펴본다. InfraWheel 산업 전체 입력에 개별 회사의 ROE·매출성장률을 직접 대입하지 않는다. 산업 모델과 기업 모델은 입력의 시장 범위와 예측 대상이 다르다.

추가 일정은 FR0 최신 조회 서비스 **5–8일**, FR1 재무 조회·쉬운 설명 **15–22일**, FR2 근거 있는 AI 심화 **7–10일**, FR3 기업 시나리오 연결 **4–6일**로 합계 **31–46 작업일**이다. 기존 36–53일은 산업 랩 범위의 추정으로 유지하고, 두 범위의 순차 단순 합계는 **67–99일**이다. 데이터 확보 대기는 별도다. 중국·홍콩 전체 자동 표준화와 금융업 전용 모델은 이 합계에 포함되지 않는다.

우선 회사 식별·재무 데이터 계약과 FR0+FR1을 개발하여 재무 기능을 먼저 출시할 수 있게 한다. 랩의 P0–P3, 산업 보정 P4/P5는 기존 목표를 유지한다. 기업 시나리오는 랩 실행·저장 계약과 재무 검증이 모두 준비된 뒤 연결한다. 구체 수식·결측 처리·시장별 공급 계획·완료 기준은 [재무제표 기능 계획](financial-statements-feature-plan.md)을 최신 기준으로 사용한다.
