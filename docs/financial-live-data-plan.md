# 재무제표 최신 조회·시세 연동 설계

작성일: 2026-09-13 · 계획, 구현 전

**결정: 재무 첫 릴리스에 서버 API와 공시 변경 확인을 포함한다.** 기존 정적 스냅샷은 빠른 첫 표시·오프라인·과거 버전 재현에 사용하고, 최신 여부는 서버에서 확인한다. [재무 기능 계획](financial-statements-feature-plan.md)의 ‘임의 종목 수집 API 후속 도입’ 안을 지원 시장·발행회사 범위의 요청 시 수집으로 변경한다.

## 데이터별 최신성

재무제표의 최신 정보는 회사가 공개한 최신 보고서다. 현재 분기의 아직 공시되지 않은 매출·이익·현금잔액을 실시간으로 알 수 있는 것은 아니다. 시세와 재무제표를 따로 조회하고 화면에 서로 다른 기준시각을 표시한다.

| 데이터 | 공급 경로 | 계획상 갱신 정책 |
|---|---|---|
| 현재 주가·시가총액·환율 | 사용 범위가 허용된 시세 제공자 API | 화면 활성 상태에서 30–60초 간격 조회를 초기 기본값으로 검토. 실제 실시간/지연/종가 구분과 거래소 시각 표시 |
| 재무 공시 목록 | 한국 DART 공시검색, 미국 SEC submissions | 화면 진입 시 최근 확인이 5분 이상 지났으면 재확인. 활성 조회 회사는 공급자 한도 내 5–15분 간격 배경 확인 |
| 재무제표 수치 | DART 재무정보, SEC companyfacts와 해당 원문 | 새 보고서·정정·facts 변경 발견 시만 수집·정규화·검증. 원문과 구조화 데이터의 게시 지연을 별도 처리 |
| PER·PBR 등 가격 의존 지표 | 최근 검증 재무 스냅샷 + 시세/주식수·기업행동 데이터 | 시세 갱신 시 재계산. 가격 시각과 재무 기간, 희석/ADR 기준을 명시 |
| 쉬운 설명·AI 해석 | 검증된 재무·주석, 버전이 고정된 분석 | 재무/근거 변경 시 갱신. 가격 판단 문장은 가격 의존성을 추적하여 낡은 가격 기반 문장을 유지하지 않음 |

이 주기는 제품 기본안이며 공급자 제공 지연·호출 한도·운영 측정에 따라 조정한다. 60초마다 지연 시세를 읽는다고 실시간 시세가 되지 않는다. 시세 공급자의 한국·미국·홍콩·중국별 실제 커버리지·재배포 조건·지연 등급은 계약 또는 사용 조건 확인 후 확정한다. 현재 yfinance 파이프라인을 실시간 보장 피드로 취급하지 않는다.

SEC는 공시 배포에 따라 API가 갱신되며 보통 submissions보다 XBRL이 늦고 혼잡 시 더 지연될 수 있다고 설명한다. 따라서 새 공시 발견 직후 companyfacts에 아직 수치가 없을 수 있다. [SEC API 안내](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)

## 종목 화면에서의 흐름

1. 앱이 거래소+티커로 발행회사를 식별하고 재무 API를 요청한다. 관심 목록 전체를 전송할 필요는 없다.
2. 서버는 검증된 기존 스냅샷이 있으면 바로 반환하고 최신 확인 필요 여부·작업 상태를 함께 보낸다. 앱은 해당 기준일의 자료를 표시한다.
3. 확인 TTL이 만료됐거나 사용자가 ‘최신 공시 확인’을 누르면 DART/SEC를 조회한다. 새 공시가 없으면 확인 시각만 갱신한다. 버튼은 수집 주기 제한을 무제한 우회하지 않는다.
4. 새 공시·정정 또는 구조화 facts 변경을 발견하면 작업 큐에서 수집→기간/단위 정규화→지표 계산→회계 대사를 실행한다. 검증한 스냅샷을 원자적으로 게시한다.
5. 앱은 job 상태를 짧게 polling하고 완료 시 새 수치를 표시한다. AI 해석은 별도 작업으로 생성하며 그동안 ‘재무 업데이트 완료·심화 해석 준비 중’을 표시한다.

처음 보는 지원 종목은 기존 수치 대신 `202 accepted + jobId`와 수집 상태를 보여준다. 식별 불가·미지원 시장은 명시적인 실패 코드로 반환한다. 신규 수집 시간은 원문 크기·API 상태에 달려 있으므로 모든 종목에 몇 초 내 완성을 약속하지 않는다. 기존 데이터 응답 속도 목표만 따로 측정한다.

## 서비스와 API 계약

Stock React 앱과 PWA는 기존 정적 호스팅에 유지한다. 별도로 작은 Node/TypeScript API, 공시 수집 Worker, 스케줄러를 배포한다. 초기에는 PostgreSQL에 snapshot metadata·확인 시각·durable job/lease를 두고 원문·버전별 결과는 object storage에 저장하는 구성을 기본안으로 한다. Redis·WebSocket·시뮬레이션 서버는 필수로 도입하지 않는다. 배포 제공자는 비용·운영 조건 확인 후 결정한다.

| API | 동작 |
|---|---|
| `GET /v1/securities/resolve?exchange=…&ticker=…` | securityId·issuerId·지원 여부 반환 |
| `GET /v1/issuers/:id/financials` | 최신 검증 snapshot 및 확인/갱신 상태. 미수집 시 제한된 최초 수집 예약 |
| `POST /v1/issuers/:id/refresh` | 중복 제거·쿨다운을 적용한 새 공시 확인 요청, jobId 반환 |
| `GET /v1/jobs/:jobId` | queued/fetching/validating/ready/failed 상태와 결과 버전 |
| `GET /v1/securities/:id/quote` | price·currency·quoteAt·delayClass·marketStatus·source 반환 |
| `GET /v1/issuers/:id/analysis?financialVersion=…` | 요청한 재무 버전과 일치하는 분석 또는 준비 상태 |

재무 응답에는 `periodEnd`, `filedAt`, `sourceCheckedAt`, `fetchedAt`, `financialVersion`, `latestKnownFilingId`, `updateStatus`, `isStale`, `analysisStatus`를 포함한다. 재무 값과 해석은 같은 버전이어야 한다. ‘공시 확인 성공’과 ‘새 공시 내용 분석 완료’를 같은 최신 상태로 표시하지 않는다. 발행 사실 확인 없이 `sourceCheckedAt`를 현재 시각으로 바꾸지 않는다.

## 운영·정확성

- 동일 issuer+filing+방법론 작업은 하나로 합치고 재시도에 idempotency를 적용한다. 정정 후에도 이전 원문·수치·분석 버전을 보존한다.
- 공시 목록은 페이지네이션과 기간 중첩 조회로 접수 누락을 줄인다. 같은 filing에 뒤늦게 붙는 XBRL 데이터는 지수 backoff 재시도와 정기 대사로 확인한다. 접수번호 변경만을 유일한 변경 조건으로 삼지 않는다.
- 공급자별 호출 예산, 인증키, 식별용 헤더, 429/오류 backoff를 서버에서 관리한다. DART 키·시세 키·AI 키를 브라우저에 보내지 않는다. 브라우저는 자체 API만 호출한다. [DART 공시검색](https://opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS001&apiId=2019001), [SEC CORS 안내](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)
- 공개 조회는 회사 식별자 allowlist/지원 registry를 사용하고 생성 작업에는 제한된 세션·요청량 제어를 둔다. 임의 URL을 대신 가져오는 공개 프록시를 만들지 않는다. 기존 계정 없는 UX를 유지해도 비용이 드는 작업을 무제한 허용하지 않는다.
- 확인 실패 시 마지막 정상 자료에 ‘최신 공시 확인 실패’를 표시한다. 오프라인에서는 마지막 저장 자료임을 표시한다. 실패한 확인이 오래된 값을 최신으로 승격시키면 안 된다.
- 재무 검증 실패는 기존 버전을 보존하고 원문 링크와 처리 상태를 제공한다. 새 수치와 이전 수치의 AI 설명을 한 분석 결과처럼 섞지 않는다.
- 시세가 없거나 지연이면 재무제표는 계속 볼 수 있으나 현재 가격 의존 지표는 해당 시각·지연을 표시하거나 계산 보류한다. ‘현재 현금잔액’이라는 표현 대신 ‘최근 공시 기말 현금’을 쓴다.

화면의 예시는 `주가: 거래소 시각 10:32, 지연 여부 표시 / 재무: 2026년 2분기 / 공시: 8월 14일 / 최신 공시 확인: 방금 / AI 해석: 같은 재무 버전`처럼 구성한다. 이는 UI 예시이며 특정 회사의 실제 시각·자료가 아니다.

## 개발 범위와 인수 기준

재무 기능 첫 출시의 선행 단계 **FR0 최신 조회 서비스 5–8 작업일**을 추가한다. 포함 범위는 지원 issuer의 요청 시 수집, API·durable job·스케줄러, 배경 재확인, 상태 UI, 시세 공급자 어댑터와 지연 표기다. 유료 실시간 피드 계약·전체 시장 커버리지 확보와 공급자 비용은 작업일에 포함하지 않는다.

FR0+FR1의 첫 재무 출시 추정은 **20–30 작업일**이며 FR2/FR3까지 재무 기능 합계는 **31–46일**, 산업 랩 전체 36–53일과 단순 합산은 **67–99일**이다. 새로 작성한 기간의 합계로 기존 일정 표를 갱신한다. 실제 시세 계약 미확보 시 실시간 표시를 완료했다고 선언하지 않는다.

인수 테스트는 cache hit/miss, 새 공시 없음/신규/정정, 공시 후 XBRL 지연, 중복 요청·Worker 재시작, API 제한·오류·오프라인, 시세만 갱신, 재무만 갱신, AI 실패를 포함한다. 각 경우 화면의 기준시각·최신 확인 상태·수치·해석 버전이 일치해야 한다. 호출량·공시 발견 지연·수집 처리 시간·실패율을 운영 지표로 기록한다.
